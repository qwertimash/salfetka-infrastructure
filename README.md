# САЛФЕТКА — панель и ноды

Единый установщик для Ubuntu 24.04 LTS, amd64/arm64 и systemd. Репозиторий
`qwertimash/salfetka-infrastructure` приватный на время разработки. После открытия
репозитория установка и обновления не требуют GitHub-токенов.

## Установка

Bootstrap `install.py` из официального репозитория проверяет Ed25519-подпись
каталога релиза и SHA-256 готового пакета прежде, чем запустить мастер.
Первоначальный источник доверия — официальный GitHub-репозиторий по HTTPS.
Для запуска нужны Ubuntu24.04, sudo/root, Python3, curl, OpenSSL и системные CA.

Пока репозиторий PRIVATE, вставьте весь блок в терминал VPS: это одна команда.
Она скрыто запросит GitHub-токен, автоматически скачает bootstrap и откроет мастер.
Токену нужен доступ только к `qwertimash/salfetka-infrastructure`, Contents: Read-only.
Токен не вставляется в саму команду, URL или аргументы процессов. Временный файл0600
в каталоге0700 удаляется при обычном завершении, ошибке и обрабатываемом прерывании.

```sh
sudo bash -c 'set +x; set -euo pipefail; umask 077
d=$(mktemp -d /tmp/salfetka-start.XXXXXXXX)
cleanup() { rm -rf -- "$d"; }; trap cleanup EXIT; trap "exit 130" INT; trap "exit 143" TERM
read -rsp "GitHub token (Contents: read): " salfetka_token </dev/tty; printf "\n"
[[ "$salfetka_token" =~ ^[A-Za-z0-9_]+$ && ${#salfetka_token} -le 4096 ]] || exit 1
printf "%s" "$salfetka_token" > "$d/token"
printf "Authorization: Bearer %s\n" "$salfetka_token" | curl -q -fsS --proto =https --tlsv1.2 --location --max-redirs 0 --connect-timeout 15 --max-time 60 --max-filesize 262144 -H @- -H "Accept: application/vnd.github.raw+json" "https://api.github.com/repos/qwertimash/salfetka-infrastructure/contents/install.py?ref=main" -o "$d/install.py"
unset salfetka_token
python3 "$d/install.py" --github-token-file "$d/token"'
```

Запрос к GitHub Contents API не следует перенаправлениям, проверяет HTTPS и
получает только bootstrap из официального репозитория. Затем bootstrap скачивает
опубликованный Release и проверяет Ed25519/SHA-256 готового установщика. Исходники
текущего main на сервере не компилируются. Первоначальное доверие — GitHub HTTPS
и официальный репозиторий, как у прежней ручной загрузки `install.py`.

Повторный запуск той же команды на установленном сервере открывает меню управления
с доступом к приватным релизам. GitHub-токен — отдельный доступ к загрузке, он не
входит в SN1-приглашение ноды. При SIGKILL/отключении питания trap не выполняется:
в `/tmp/salfetka-start.*` может остаться root-only временный файл до очистки /tmp.

После открытия репозитория доступен запуск без токена:

```sh
download_dir=$(mktemp -d)
curl -fL --proto '=https' --tlsv1.2 https://github.com/qwertimash/salfetka-infrastructure/releases/latest/download/install.py -o "$download_dir/install.py" && sudo python3 "$download_dir/install.py"
```

Прежний `--github-token-file /root/github-read-token` (файл0600) сохраняется для
операторов, использующих собственное хранение токена и прямой `salfetka check/update`.

Мастер предлагает три варианта:

1. **Панель и нода.** Два домена панели/подписок, собственный домен ноды, публичный
   IP, email для ACME, логин/пароль владельца. Панель создаёт физический сервер и
   выдаёт приглашение сама; копировать код между этапами не нужно.
2. **Только нода.** Вставьте один скрытый код из своей авторизованной панели.
   Мастер извлечёт адрес и доверие, проверит TLS и покажет origin, ID, срок и
   отпечатки. Токен отправляется только после явного подтверждения адреса. Домен и IP
   нода получает от панели по mTLS после регистрации; отдельно нужен только email
   для Let’s Encrypt, повторный ввод IP/домена или перенос PEM не нужен.
3. **Только панель.** Те же вопросы о панели; ноды добавляются позже через UI.

Вариант «панель» использует TCP 443 для web/подписок. В совмещённом варианте web
и подписки используют HTTPS 9443; TCP/UDP 443 остаются VPN-ноду. В обоих вариантах
TCP 18443 — отдельный проверяемый TLS-вход для нод. DNS A/AAAA должен вести на
этот сервер, входящий TCP 80 нужен Let’s Encrypt. Установщик не переписывает пользовательские правила firewall/DNS
и не удаляет чужие службы. Docker публикует перечисленные TCP-порты на IPv4/IPv6. Установщик использует только локальный Unix socket Docker: внешний context не затрагивается. Рабочие Docker/Compose переиспользуются без замены пакетов или перезапуска Docker; несовместимая существующая установка сохраняется и требует исправления оператором. Занятый порт или чужой ресурс останавливает установку.

Публичные сертификаты ACME продлеваются отдельным systemd timer дважды в сутки.
Их продление не меняет доверие установленных нод: машинный сертификат и signer
сохраняются отдельно. Машинный сертификат рассчитан на 10 лет; его замена требует
отдельной процедуры ротации доверия, а не обычного обновления пакета.

Установка ноды подтверждает защищённую связь с панелью. VPN-подключения и состав
подписок настраиваются в панели; heartbeat не означает прохождение VPN-трафика.
Начиная с 0.7.0 установщик автоматически создаёт сайт ноды и выпускает отдельный
сертификат её домена. В мастере подключений выберите TCP Reality, Hysteria2, gRPC,
XHTTP: готовый TLS берётся с ноды, без ввода PEM. Перед созданием требуется свежий
отчёт готовности сайта; прежняя ручная настройка остаётся в отдельном режиме.

Сайт сразу доступен по `https://домен-ноды:8445`. Reality использует собственный
SNI и target `127.0.0.1:8445`; после его включения сайт доступен также на HTTPS443.
TCP80 обслуживает только сайт и HTTP-01; TCP8443/8444 предназначены для gRPC/XHTTP.
Для новой ноды нужны свободные TCP80/8445 и корректные A/AAAA. Установщик отвергает
дополнительные DNS-адреса, не принадлежащие этому серверу. Сам DNS у провайдера
настраивается владельцем до запуска установщика.

Certbot работает в отдельном каталоге `/opt/salfetka-manager/node-acme`. Приватный
TLS-ключ не передаётся панели: нода читает root-owned `/opt/salfetka-nodes/main/site/bundle.pem`
только на чтение. Пара cert/key проверяется (цепочка доверия, SAN, срок и соответствие)
и заменяется одним атомарным действием. Сбой ACME сохраняет рабочую пару. Сайт
подхватывает сертификат при новых handshake; только подключения с TLS ноды
перезапускаются при его смене. Их активные сессии кратковременно прервутся; Reality
и подключения с ручными PEM не перезапускаются при обычном продлении.

Сайт работает под отдельным временным пользователем systemd, без доступа к
identity и конфигурации агента. Каталог и TLS bundle доступны ему только на чтение;
ключ регистрации ноды отделён от публичного веб-процесса.

В совмещённой установке продление сертификатов панели использует тот же HTTP-01
webroot. Сайт и VPN для этого не останавливаются. `salfetka renew` проверяет выпуск
и реальную активацию; `salfetka status` проверяет HTTPS/H2 сайта. Ошибки таймера:
`journalctl -u salfetka-certificate.service`. Сертификаты не обновляют версии программы.
Пункт «Остановить» останавливает панель/VPN-агент; сайт и HTTP-01 остаются доступны
для продления сертификатов. Для полной остановки веб-сайта используется
`sudo systemctl stop salfetka-node-site.service` (HTTP-01 на время остановки недоступен).
После ошибки выпуска исправьте DNS/доступность80 и повторите установку: уже
зарегистрированная identity сохраняется. Self-signed сертификат вместо ACME не выдаётся.

Для существующей установки 0.6.x: сначала обновите установщик, затем панель и ноду
до 0.7.0, после чего выполните `sudo salfetka site` (пункт8 меню). Это явно добавляет
сайт на TCP80/8445 и выпускает сертификат. Существующие подключения с ручными PEM
не переводятся в новый режим автоматически; новые создаются без PEM. Для режима
«только нода» сначала обновите удалённую панель: старый API не выдаёт metadata сайта.

На сервере нужна согласованная синхронизация времени. Конкурирующие NTP и
периодический перевод часов гипервизором могут накопить откат больше секунды:
нода намеренно остановится, чтобы не продлевать выданный доступ. При таком отказе
исправьте источники времени и запустите службу снова; не удаляйте identity или
сохранённые отметки времени. Малую разницу при обычном перезапуске нода ждёт до
достижения сохранённой отметки, не понижая её.

## Обновления и управление

```sh
sudo salfetka
sudo salfetka status
sudo salfetka check
sudo salfetka update
sudo salfetka update --component panel --version 0.7.0
sudo salfetka update --component node --version 0.7.0
sudo salfetka backup
```

Каждый релиз содержит готовый Docker-образ панели, бинарники ноды и мастер для
обеих архитектур. Код не берётся из текущего `main`; на сервере ничего не
компилируется. Перед обновлением проверяются подпись, срок каталога, архитектура,
протокол и schema. Downgrade отклоняется. Затем создаётся приватная резервная копия,
обновляются выбранные компоненты и проверяются readiness/heartbeat. Проверка
готовности ждёт запуска всех служб и публикации их имён во внутреннем DNS Docker;
постоянная ошибка конфигурации/TLS по-прежнему останавливает операцию. Ключи,
пользователи, ссылки подписок, настройки и регистрация нод сохраняются.

Проверка образа поддерживает classic Docker и containerd: их локальные image ID
могут различаться. После импорта установщик сверяет неизменяемую конфигурацию
образа (включая хеши слоёв) с подписанным архивом; одного совпадения тега недостаточно.

Для служебных PRIVATE-версий `0.6.0`–`0.6.5` сначала обновите сам установщик,
затем повторите команду уже новым процессом:

```sh
sudo salfetka update --component installer --version 0.7.0 --github-token-file /root/github-read-token
sudo salfetka update --version 0.7.0 --github-token-file /root/github-read-token
```

Так новые проверки установщика выполняются уже в новом процессе. Самые ранние
сборки также ещё не учитывали различия image ID classic/containerd.
В новой установке с `0.7.0` используется обычный `salfetka update`.

`/opt/salfetka-manager/state.json` хранит установленные версии, `transaction.json`
— этап незавершённой операции. Ошибка не отмечается как успех. Повторный `update`
продолжает записанную целевую версию. После прерванной установки повторите
`salfetka install --role panel|node|both`; существующая identity не пересоздаётся.
Повторная регистрация возможна, пока её одноразовый код действителен; истёкший
неиспользованный код нужно перевыпустить в панели. Каталоги частичной установки
не удаляются автоматически.

## Резервная копия и восстановление

Копия содержит транзакционный pg_dump, конфигурацию/ключи и точные подписанные
пакеты установленных версий. Доступ только root. Копии нужно хранить вне сервера.

```sh
sudo salfetka restore --backup-dir /opt/salfetka-manager/backups/DATE-ID
sudo salfetka start
```

Восстановление проверяет целостность и принадлежность копии, импортирует её в
**отдельную неактивную БД**, сохраняет предыдущую БД и затем переключает DSN.
Браузерные сессии, неиспользованные приглашения и старые bypass leases не
восстанавливаются как активные. Панель остаётся остановленной до явного запуска.
Данные, включая права/отзывы, возвращаются к дате копии: изменения после этой даты
нужно сверить перед запуском. Локальные ключи и состояние нод не заменяются.
Это восстановление существующей установки с совпадающими ключами; перенос на
новую машину и восстановление утраченных node identity — отдельная процедура.
Отдельного пункта «откат версии панели» нет.

## Выпуск версии

Workflow **Build and publish signed release** запускается вручную с новой
неизменяемой версией X.Y.Z. Он собирает и тестирует обе архитектуры, затем отдельный
job подписывает каталог ключом `SALFETKA_RELEASE_SIGNING_KEY` из GitHub Secrets и
публикует Release. Приватный ключ не входит в исходники, образы или пакеты.
Повторная публикация изменённого manifest под тем же номером отвергается клиентом.
Изменение открытого ключа — отдельная миграция, не рядовое обновление.

При ошибке миграции или health check службы могут остаться остановленными.
Исправленный релиз либо проверенное восстановление — путь восстановления работы;
автоматической подмены версии или восстановления старой БД нет.
